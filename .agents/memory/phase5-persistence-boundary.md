---
name: Phase 5 persistence boundary
description: Operational boundary for task orchestration and generated artifacts after Phase 5.
---

The Phase 5 scaffold originally kept task groups and artifact metadata in
process-local stores, while generated bytes used a local temporary directory.
The user has since explicitly asked for database-backed persistence throughout
this system; the earlier boundary against adding durable storage is superseded
for future work.

**Why:** The phase explicitly focused on finite orchestration, skill execution,
and tenant/user access contracts without introducing a new persistence schema
or changing the existing database boundary.

**How to apply:** Use the existing project database as the source of truth for
durable application state, messages, sessions, and failure status. Add
tenant-scoped records, ownership checks, expiry cleanup, and restart/recovery
tests for any feature that promises persistence. Do not silently replace the
current database or persist ephemeral runtime objects that cannot be restored.

The artifact renderers are provisioned through `replit.nix` Nix packages in
this workspace. The generic Python package installer may target an unavailable
managed interpreter, so verify imports in the workflow runtime rather than
trusting `requirements.txt` alone.

**Why:** The renderer dependencies were present in the project requirements
but absent from the active Python environment until system-level packages were
added and imports were verified.

**How to apply:** For future artifact work, keep the Python requirements
declarations and Nix runtime packages aligned, then verify the actual runtime
imports and file signatures before declaring production artifact support.

The user explicitly requested: use the database for everything in this system
and avoid silent failures. Durable state must not depend only on process memory;
runtime handles such as an open Baileys socket remain process-local and must be
recovered from database-backed credentials and status.

**Why:** The user asked that system data and errors use the database so failures
are easier to recover and diagnose.

**How to apply:** Persist durable messages, session credentials, inbound
processing status, delivery state, and error categories in the existing MongoDB
store. Keep only transient handles and caches in memory, and make failures
visible rather than swallowing them.
