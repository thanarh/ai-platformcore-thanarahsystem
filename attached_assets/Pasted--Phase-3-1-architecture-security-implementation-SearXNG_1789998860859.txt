# PHASE 4 — THANARAH AI GATEWAY + TOOL / SKILL FOUNDATION

الهدف:

تحويل Thanarah Intelligence من Chatbot إلى Intelligence Layer يستطيع مستقبلًا استخدام capabilities حقيقية، مع صلاحيات وtenant isolation وaudit.

لكن:

**لا نبني Agent كامل الآن.**

# 1. Core Architecture

نفذ:

```text
User
 ↓
Conversation
 ↓
AI Orchestrator
 ↓
Capability Decision
 ↓
┌──────────────┬──────────────┬──────────────┐
│ Local Model  │ Web Search   │ Thanarah     │
│              │              │ Core Tools   │
└──────────────┴──────────────┴──────────────┘
                       ↓
                 Validated Result
                       ↓
                    Qwen
                       ↓
                    Response
```

ولا تجعل الـ model يتصل مباشرة بأي database أو service.

---

# 2. AI Gateway

أنشئ service/layer واضح باسم:

```text
AIGateway
```

مسؤوليته:

* receive request
* authenticate context
* resolve tenant/user
* determine available capabilities
* validate tool request
* enforce permissions
* execute capability
* normalize result
* return result to model
* emit streaming events
* audit execution

لا تضع كل هذا داخل Chat controller.

# 5. لا تخترع Thanarah APIs

هذه نقطة CRITICAL.

إذا لم يوجد API contract حقيقي لـ Thanarah Core في المشروع:

لا تدّعي أن integration حقيقي.

اعمل:

```text
ThanarahCoreAdapter
        ↓
MockThanarahCoreAdapter
```

والـ mock data يجب أن تكون واضحة على أنها:

```text
TEST / DEVELOPMENT DATA
```

ولا تظهر للمستخدم كأنها بيانات حقيقية.

جهز الـ adapter بحيث استبداله بالـ real Thanarah Core API لاحقًا لا يحتاج إعادة بناء الـ AI Core.

# 6. Tenant Context

كل execution يجب أن يحصل على server-side context:

```text
tenantId
organizationId
userId
conversationId
requestId
```

ولا تسمح للـ model بإرسال tenantId أو userId ليغير authenticated context.

مثال:

```text
Model:
tenantId = clinic-B

Server authenticated context:
tenantId = clinic-A

Result:
REJECT
```

# 7. Permissions

أضف permissions:

```text
appointments.read
doctors.read

insurance.read
clinic.read
```

كل Tool تحدد permissions المطلوبة.

مثال:

```text

→ appointments.read
```

إذا لم توجد permission:

```text
TOOL_FORBIDDEN
```

ولا يتم التنفيذ.

# 8. Tool Execution

الـ flow الإجباري:

```text
Model proposes tool
        ↓
Tool exists?
        ↓
Schema validation
        ↓
Permission validation
        ↓
Tenant validation
        ↓
Execute
        ↓
Validate result
        ↓
Return structured result
        ↓
Model generates answer
```

الموديل لا يستطيع تجاوز أي خطوة.

---

# 9. Tool Calling

لا تعتمد على regex من النص.

استخدم structured tool request.

مثال:

```json
{
  "tool": "get_appointments",
  "arguments": {
    "date": "2026-09-22"
  }
}
```

ثم backend يتحقق من schema.

إذا arguments غير صحيحة:

```text
TOOL_INVALID_ARGUMENTS
```

ولا ينفذ الطلب.

# 10. Date / Time

مثال:

```text

```

يتم تحويلها إلى تاريخ فعلي حسب:

```text

```

وليس timezone السيرفر.

احتفظ بالـ resolved value في execution metadata.

# 11. Routing

ابدأ capability routing بسيطًا:

```text
General knowledge
→ Local Qwen

Current external information
→ Web Intelligence

Explicit web search
→ Web Intelligence

Thanarah operational data
→ Thanarah Tool
```

مثال:

```text
"اشرح API"
→ Local

"ابحث عن آخر أخبار التقنية"
→ Web

"كم موعد عندي بكرة؟"
→ Thanarah Tool
```

لكن Web Search حاليًا disabled بسبب البيئة.

لذلك لا تحاول استخدامه أو fake results.
