أريد منك الآن تطوير نظام الذكاء الاصطناعي الموجود في هذا المشروع، لكن **لا تعيد بناء المشروع من الصفر ولا تستبدل الـarchitecture الحالية بالكامل**. سنطوره تدريجيًا إلى AI Engine قوي سيكون لاحقًا الـAI Core لمنصة Thanarah Core، وسيتم دمجه مع WhatsApp والعيادات والموقع وموظفي العيادة.

## الهدف النهائي للمشروع

نريد بناء Local AI Infrastructure تعتمد على Open Source فقط، بدون أي مدفوعات إضافية وبدون الاعتماد على OpenAI أو Anthropic أو Gemini أو Groq أو OpenRouter أو أي AI API خارجي.

الموجود حاليًا يجب الحفاظ عليه، خصوصًا:

* Next.js frontend
* NestJS backend
* Python/FastAPI AI engine
* MongoDB
* Ollama
* Qwen 2.5 7B
* Authentication
* Conversations
* Memory
* RAG/Knowledge functionality
* Streaming إن كان موجودًا
* Multi-tenant architecture
* Existing APIs

لدينا Render server بموارد تقريبية:

* 12 CPU
* 24 GB RAM

ولا أريد إضافة أي خدمة مدفوعة.

# PHASE 1 — PERFORMANCE ENGINE

المشكلة الحالية أن بعض الردود قد تنتظر حوالي 8 ثوانٍ قبل ظهور الرد.

أريد تحسين تجربة الاستجابة من خلال البرمجة فقط.

## 1. LATENCY TELEMETRY

أضف request-level performance tracing بدون أي external paid service.

لكل AI request سجل داخليًا:

* requestId
* routerMs
* memoryMs
* retrievalMs
* embeddingMs
* promptBuildMs
* ollamaQueueMs
* modelLoadMs إن أمكن
* timeToFirstTokenMs
* generationMs
* totalMs
* inputTokens إن أمكن
* outputTokens إن أمكن
* model
* route
* cacheHit

لا تسجل بيانات حساسة للمريض في logs.

أريد أن نعرف بالضبط أين تذهب الـ8 ثواني.

---

# 2. TRUE STREAMING

افحص الـstreaming الحالي.

إذا كان النظام يولد الرد كاملًا ثم يرسله للواجهة، أصلح ذلك.

المطلوب:

User sends message
→ request starts
→ first token/chunk يتم إرساله فور توفره
→ باقي الرد يصل تدريجيًا

لا تنتظر اكتمال generation لإرسال أول جزء.

استخدم الـstreaming الموجود في Ollama إن كان متاحًا، وحافظ على SSE أو الآلية الحالية المناسبة للمشروع.

لا تضف WebSocket إلا إذا كان ضروريًا فعلًا.

---

# 3. OLLAMA WARM MODEL

تأكد أن Qwen لا يتم تحميله من جديد لكل request.

اعمل model warm-up عند تشغيل AI service.

تحقق من:

* model availability
* model loaded state إن أمكن
* connection reuse

الهدف تقليل cold-start latency.

---

# 4. PROMPT OPTIMIZATION

افحص الـprompt الحالي.

لا ترسل conversation history بالكامل مع كل request.

طبق context management:

* Recent messages
* Conversation summary
* Relevant memory
* Relevant retrieved knowledge

بدل إرسال تاريخ المحادثة بالكامل.

لكن لا تكسر conversational context.

أضف limits واضحة للـcontext.

---

# 5. PARALLEL RETRIEVAL

إذا كان Memory retrieval وKnowledge retrieval مستقلين، شغلهما بالتوازي بدل تنفيذ:

Memory
ثم
Knowledge

استخدم async/concurrent execution حيث يكون آمنًا.

نفس الفكرة لأي عمليات مستقلة أخرى.

لا تستخدم parallelism إذا كان سيؤدي إلى race conditions أو data leakage بين tenants.

---

# 6. RESPONSE CACHE FOUNDATION

أضف caching layer داخلية بدون أي خدمة مدفوعة.

ابدأ بـ exact-request cache فقط.

لا تستخدم semantic cache الآن قبل أن نفهم الـbaseline.

Cache key يجب أن يأخذ في الاعتبار على الأقل:

* tenantId
* relevant configuration
* normalized user query
* model
* knowledge version إن كان السؤال يعتمد على knowledge

ولا تسمح أبدًا بتسريب response من Tenant إلى Tenant آخر.

أضف cacheHit وcacheMiss إلى telemetry.

---

# 7. CPU / MEMORY OPTIMIZATION

افحص إعدادات Ollama الحالية.

لدينا 12 CPU و24 GB RAM.

لا تغير model بشكل عشوائي.

أريد أولًا benchmark للـQwen الحالي.

اختبر إعدادات مناسبة للـCPU مثل:

* threads
* context size
* batch size
* parallel requests

لكن لا ترفع القيم لمجرد رفعها.

نريد قياس:

* TTFT
* tokens/sec
* total latency
* RAM
* CPU

ولا تستخدم GPU لأن البيئة الحالية CPU-based.
